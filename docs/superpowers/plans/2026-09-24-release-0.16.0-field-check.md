### 1.4 How to see connection details and force the signals carrier

1. In the room, turn on the toggle at the bottom labelled "Show connection details" (it then reads "Hide connection details"). Source: trunk `ui/src/room/room-view.ts`, `renderConnectionDetailsToggle`. The toggle is hidden while a tile is maximized.
2. With details on, each peer tile shows a stats strip. Its first word is the carrier: "WEBRTC" or "SIGNALS" (the code value is lower case and CSS shows it upper case, `ui/src/room/elements/peer-stats-panel.ts`).
3. With details on, a carrier selector appears: "Carrier:" followed by two buttons, "WebRTC" and "Signals" (`room-view.ts`, `_renderCarrierSelector`). Click **Signals** to force the signals carrier for all peers. Click **WebRTC** to go back. One side is enough: the choice travels to peers in the conversation module payload.
4. The choice persists across sessions (local storage key `disableAllWebrtc`). Set it back to **WebRTC** at the end of every section that changed it.

### 1.5 How to export logs

1. Turn on connection details (1.4).
2. A cloud-download button appears to the left of the toolbar. Its tooltip reads "Request diagnostic logs from all peers on call" (`room-view.ts`, `renderToggles`).
3. Click it once. While it asks peers, the icon is amber. When at least one peer answered, the icon turns green ("Download merged logs from N peer(s) + local").
4. Click the green button. The browser saves `Presence_merged_0.16.0_<date>.json`. It holds the local log and every peer that answered.
5. Search the file for the event name as text, for example `SystemAudioEnded`. Each event is a JSON object with an `event` field and, for most events, a `detail` field. Event names are declared in `SIMPLE_EVENT_TAXONOMY` (`ui/src/logging.ts`).

If no peer answers after three attempts, the icon turns red ("No peers responded after 3 attempts — click to retry"). Retry once. If it stays red, record that in the notes of the step you were on.

## 2. Stable tile order (Task 7, Step 1)

What the code does: peer tiles are sorted by the time each agent first joined the room, ever. That time is the timestamp of the agent's ALL_AGENTS anchor link. The room zome's `init` writes this link once per cell (`dnas/presence/zomes/coordinator/room/src/all_agents.rs`, trunk `ui/src/room/tile-order-policy.ts`). Your own tile is not part of that sort. It is always drawn first, before the peer tiles. A peer whose link has not reached you yet sorts at the end until the next poll.

Setup: you need three agents. Use A, B, and a third agent C. C is a second Moss instance on machine B, started with a separate profile: the Moss command-line option `--profile <name>` (Moss `src/main/index.ts`). C joins the same group and installs the same 0.16.0 Tool. All three are on the new Moss.

1. Create a new room in the 0.16.0 Tool. Nobody must be in its history yet.
2. Agent A enters the room. Wait 10 seconds.
3. Agent B enters the room. Wait 10 seconds.
4. Agent C enters the room. Wait 30 seconds so that every agent's poll has seen every link.
5. On each screen, write down the order of the peer tiles, left to right, top to bottom.
   Expected: A sees "self, B, C". B sees "self, A, C". C sees "self, A, B". The peer tiles keep the order A, B, C on every screen, with the viewer's own tile left out of that list.
6. Agent C leaves the call ("Leave Call" button) and enters again. Wait 30 seconds.
   Expected: on A and B, C's tile comes back in the same slot as before. No other tile moves.
7. Agent A leaves the call and enters again. Wait 30 seconds.
   Expected: on B and C, A's tile comes back in the first peer slot, not at the end.
8. Optional: on machine A, turn on connection details and watch the grid for one minute during a normal call.
   Expected: no tile changes position while nobody joins or leaves.

## 3. System audio (Task 7, Step 2)

This is the owner checklist from Task 6 of `docs/superpowers/plans/2026-09-23-presence-system-audio.md`, updated for current behavior. Two v1 rules were removed by the two-machine round (CLAUDE.md, System-audio bullet, "Sharing without the microphone"):

- A share no longer needs the microphone.
- Mute now silences only the microphone. The shared audio keeps going out. v1's step 4 ("peer hears neither voice nor music") is no longer the expected result.

Machine A shares. Machine B listens. Both are on the new Moss with 0.16.0. Keep the mic on both sides unless a step says otherwise. Use headphones on B, so that B's own speakers cannot leak into A's microphone.

Where the row is: click the small up-arrow on the right edge of the microphone button. A menu opens with the title "Audio Input Source" and one row per microphone. The last row, below a divider, is the system-audio row (trunk `ui/src/room/room-view.ts`, `_renderSystemAudioRow`). When the host does not offer `captureAudioSources`, the row is not shown (`StreamsStore.canCaptureAudioSources`).

Row texts (all from `_renderSystemAudioRow`):

- Idle: "Include audio from…"
- Moss picker open: "Choosing sources…" (row disabled)
- Sharing: "✓ Including: System audio". If Moss cannot keep its own playback out of the capture, " (may echo)" is added. "System audio" is the label Moss builds for the system choice (Moss `src/main/audioSourceGrants.ts`, `describeSelection`). For a chosen app it is the app name instead.

### 3.1 Share over WebRTC

1. A and B join the same room with mics on. Turn on connection details on both.
   Expected: B's tile for A shows "WEBRTC" in the stats strip, and A's tile for B shows the same.
2. A opens the mic menu and clicks "Include audio from…".
   Expected: the row reads "Choosing sources…". Moss opens a dialog titled "Share audio with <Tool name>". It lists "All system audio (except Moss)" and one row per app that has audio output (Moss `audio-source-picker-dialog.ts`).
3. A selects "All system audio (except Moss)" and clicks **Share**.
   Expected: the row reads "✓ Including: System audio". Moss shows a chip: "<Tool name> is using system audio · <elapsed time>" with a **Stop** button (Moss `audio-source-chips.ts`). Record whether "(may echo)" appears.
4. A plays music.
   Expected: B hears the music mixed with A's voice.

   Expected: the music continues for B without a break. A's voice now comes from the new microphone. Switch back afterwards.

## 6. Mixed room (removed 2026-09-24)

This section was removed. A 0.15.6 install and a 0.16.0 install never share a network seed, because Moss gives every new Tool install a new random seed (Moss `group-store.ts`, `installAndAdvertiseApplet`). So no user can put a 0.15.6 agent and a 0.16.0 agent in one room. Compatibility with 0.15.x is not a goal (plan, "Decisions").
